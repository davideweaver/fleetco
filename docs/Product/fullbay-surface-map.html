The headline: 64 screens is not 64 problems. Every screen in FullBay reduces to one of eight archetypes. Build the eight well and the rest is configuration — a model, a column set, a form schema. That is the difference between a two-year build and a tractable one.

Three things inflate the apparent size and shouldn't. The service-order list has 13 tabs, but they are 13 saved filters over one list — one screen. 38 reports are one parameterised viewer. ~20 settings pages are one form archetype repeated. Together that is ~70 apparent pages collapsing to three real ones.

And one thing is genuinely hard. The Service Order → Action Item editor is a nested, multi-tab, multi-role editor with parts, labor, authorization state, and photos per line. It is one screen and plausibly a quarter of the entire frontend effort. Everything else is ordinary.

Does the navigation need hierarchy?

No — two levels is enough on the shop side, one on the portal. Nothing observed in FullBay goes deeper than section → record → tab, and the tabs are within-record, not navigation.

What the shell needs: a flat primary nav of roughly nine sections (Service, Schedule, Customers, Units, Parts, Purchasing, Time, Invoicing, Reports) plus Settings; saved views as a first-class concept on every list, because that is how FullBay's 13 SO tabs actually work; and a global search, since deep hierarchy is what you'd otherwise need to find a unit by VIN.

Role changes the nav, not its depth. A technician sees Tech Home and their jobs — perhaps three items. A service writer sees most of it. That is permission filtering over one flat structure, not a second information architecture.

What this implies for scope

ObservationConsequence for the build
8 archetypes cover 64 screensBuild the archetypes as real components first. Then most screens are a schema plus a column set — exactly the shape agent-written code is good at.
One screen is disproportionately hardThe SO → Action Item editor should be prototyped early, by hand if necessary. It is the main schedule risk on the frontend.
38 reports, no report builderReports are a data problem, not a UI one. One viewer plus 38 queries — and the client will not need all 38 at cutover.
Portal needs no auth systemTokenised per-customer URL. Removes a whole subsystem — but note it also means link-holder-equals-access.
~58 entities, ~20 coreThe long tail (statements, credit memos, core returns, vendor bills) is where replacement projects overrun. Most are not needed for customer one.
No native app in useFleetco already runs the web app bookmarked to a home screen. A PWA covers it; two native apps are avoidable.

Confidence and provenance. Module and feature names come from the Feature Inventory Draft, which combined public sources with a logged-in walkthrough of a live FullBay account — so module boundaries, the service-board stages, the portal sections, and the 38 report names are observed, not guessed.

What is inferred and should be checked: the screen counts, the entity count, the archetype assignment, and every effort-share bar. Those are my reading of the inventory, not a screen-by-screen audit. The settings count (~20) is the softest number here. Use this to size the problem and brief the client — not to estimate a schedule.

Known gap: this maps FullBay as it exists. It says nothing about which parts Fleetco actually uses — that is the markup exercise (M3), and it will remove a meaningful fraction.
