## Overview

Internal-consistency audit of the Fleetco architecture knowledgebase, run 2026-10-09 against all
20 documents. The knowledgebase was written in one session during which the platform choice
reversed twice (Supabase → Neon → AWS-native), deployment changed from siloed-per-tenant to
pooled, and subdomain tenant routing was withdrawn. This document records the residue those
reversals left, what was corrected, and what was deliberately left alone.

**Why this record exists.** These documents are the specification a build will run from, so a
stale statement is an active hazard rather than untidiness. Keeping the audit trail means a later
reader can tell the difference between "this was checked and is correct" and "this was never
looked at."

**Scope of the fix pass.** Dave approved **mechanical corrections only** — stale figures, broken
cross-references, wrong ADR numbers, and decisions marked `SUPERSEDED` in the ADR log but still
described as current elsewhere. Void rationales, claims wrong on the technical merits, and the
uncovered-domains list are being handled in a separate pass and were **not touched**.

Status key: `APPLIED` · `DEFERRED` · `REJECTED` (re-checked, not actually a defect)

Finding categories:
1. Stale figures · 2. Void rationales · 3. Direct contradictions ·
4. Superseded in one place only · 5. Orphaned or wrong cross-references ·
6. Wrong on the technical merits

## Tier 1 — Contradictions and live hazards

### F1. `Hosting and Deployment.md` still describes Neon as the current platform
**Lines 25, 44, 59–61, 131, 138, 209–213 · cat. 3 + 4 + 2**

Six separate passages name Neon as the chosen state layer, in a document whose frontmatter reads
`updated: 2026-10-09`. The final section is an explicit statement of the opposite of ADR-023:
*"ADR-010 chose Neon for database branching… that remains the differentiator. Aurora Serverless v2
is the natural fallback if Neon ever stops fitting."* Line 25 is additionally an orphaned
cross-reference — it attributes the Neon choice to `Stack Evaluation.md`, which no longer says it.

| Sub-item | Status | Note |
|---|---|---|
| L25 — "put the stateful services on Neon — Postgres, auth, and object storage" | `APPLIED` | Now Aurora Postgres + S3. "Auth" dropped from the list: auth is self-hosted in-process per ADR-012 and is no longer a platform-supplied service |
| L44 — requirement 7, "Authenticated networking to Neon" | `APPLIED` | → Aurora |
| L59–61 — "Neon is in that path, and if Neon is down…" | `APPLIED` (name only) | Vendor name corrected to Aurora. Whether the availability-product argument still holds for an in-VPC AWS service is a merits question — see F2 |
| L131 — NAT gateway, "Neon is a TLS public endpoint anyway" | `DEFERRED` | Void rationale. Aurora sits in a private subnet, so the evidence for the public-subnet option no longer exists and the decision may flip |
| L138 — "Region must match Neon's region" | `APPLIED` | → the Aurora cluster's region |
| L209–213 — "Recorded So It Is Not Re-Litigated" | `DEFERRED` | **Highest-risk remaining item.** The section is a Q&A defending Neon over Aurora; it is now backwards end to end. Correcting it means writing a new argument or deleting the section, neither of which is a mechanical edit |

### F2. ADR-021's primary rationale is Neon carrying the state
**`Architecture Decisions.md` 459–462, 516, 517 · cat. 2**

ADR-021 is `PROPOSED` (live) and its first rationale is *"The compute layer is genuinely simple,
because Neon carries the state. ADR-010 and ADR-019 put Postgres, auth, and object storage on
Neon."* ADR-019 is itself `SUPERSEDED`, so the citation points at a withdrawn decision. The
conclusion survives — Aurora and S3 also leave compute stateless — but the stated reason is void.

Note that ADR-023 and `Platform Choice.md` both cite line 517 as *"a point already conceded in
[[Hosting and Deployment]]"*, so a void rationale is being used as supporting evidence for the
decision that voided it.

- L516 ("latency to Neon matters more than latency to users"): `APPLIED` — vendor name corrected.
- L459–462 and L517: `DEFERRED` — void rationales, out of scope for this pass.

### F3. Aurora fast clone cannot work across the ADR-025 account split
**`Platform Choice.md:103`, `Architecture Decisions.md:646`, `Environments.md:82–83`,
`Infrastructure Checklist.md:102` · cat. 6 · `DEFERRED`**

`Platform Choice.md:103` records the constraint plainly: fast clone is *"same region and account,
maximum 15 clones per cluster."* ADR-025 mandates separate `prod` and `nonprod` AWS accounts. Yet
tier 4 of the dev-database workflow — a clone **of production**, used for migration rehearsal — is
specified as the replacement for Neon branching.

As written, the only way to use tier 4 is to run development work inside the production account,
which defeats ADR-025's stated purpose. Tier 3 (`staging` restored from scrubbed production) has
the same unaddressed boundary crossing, and the scrubber has no specified home.

This is not reversal residue. It is two individually correct decisions that do not compose, and it
needs a decision rather than an edit.

### F4. Vercel previews cannot authenticate against `staging` under the cookie policy
**`Architecture Decisions.md:631`, `Environments.md:67–69`, `Auth and Identity.md:142–144` ·
cat. 6 · `DEFERRED`**

ADR-024 makes "Vercel's free frontend previews pointed at `staging`" the replacement for the
dropped per-PR preview environments. ADR-013 specifies `SameSite=Lax` cookies, and
`Auth and Identity.md:142–144` requires the API be served same-site — warning specifically that
*"a Vercel frontend plus a Fly API on unrelated domains is cross-origin cookie territory."* A
preview on `*.vercel.app` calling `staging.app.fleetco.com` is exactly that case, so session
cookies will not be sent.

The stated mitigation for dropping preview environments therefore does not work for any
authenticated screen, which is nearly all of them. Needs a decision: serve previews under a
`fleetco.com` subdomain, or accept that they cover unauthenticated UI only.

### F5. ADR-022 rule 5 forbids the stack ADR-023 chose
**`Architecture Decisions.md:536–537` · cat. 3 · `DEFERRED`**

Rule 5 reads *"No proprietary platform services for anything structural… its database, queue, and
storage products may not [be used]."* ADR-023 puts the database on Aurora and storage on S3, and
ADR-015 puts the event transport on Postgres `LISTEN/NOTIFY`. Both ADRs are `PROPOSED`.

A coding agent reading rule 5 literally would reject Aurora and S3. The intent is clearly "no
*non-portable* platform services" — Postgres-the-protocol and S3-the-API are both portable — but
restating the principle is authorship, not a mechanical fix.

### F6. ADR-022 rule 3 still mandates Redis
**`Architecture Decisions.md:532` · cat. 3 · `APPLIED`**

*"Uploads to object storage, sessions to Postgres, cache to Redis."* ADR-023:593 states "Redis is
eliminated" and `Evolution Path.md:134` lists Redis among deliberate non-goals. The Redis clause
was struck.

**Consequence worth noting:** there is now no caching strategy anywhere in the knowledgebase.
That is a gap, not a contradiction, and belongs to the separate missing-domains pass.

### F7. `Realtime and Events.md` headline decision and diagram still say Redis
**Lines 12–15, 44 · cat. 3 · `APPLIED`**

The document's core decision — *"fanned out across API instances via Redis"* — and the
architecture diagram (`└──► Redis pub/sub`) contradicted the revised decision 80 lines later at
line 128, which cites ADR-023. The overview and the diagram are what a reader hits first. Both now
read `LISTEN/NOTIFY`.

### F8. ADR-015's decision text contradicts its own revision note
**`Architecture Decisions.md:281` vs 295–300 · cat. 3 · `APPLIED`**

The **Decision** paragraph specified Redis pub/sub; the revision note below it says Postgres
`LISTEN/NOTIFY` replaces Redis. The decision statement was never amended. Corrected, because the
revision note makes the replacement unambiguous.

### F9. "Production must never scale to zero" lives only in a superseded ADR
**`Environments.md:105–106`, `Architecture Decisions.md:643–644` → ADR-019:396–398 · cat. 5 ·
`DEFERRED`**

Two documents attribute the rule to ADR-021 (*"ADR-021 forbids it in production"*). ADR-021 says
nothing about scale-to-zero; the rule appears in ADR-019, which is `SUPERSEDED by 023`.

Deferred rather than re-pointed, because the citation is half-defensible and the correct target is
a judgment call. ADR-021 **does** effectively forbid compute scale-to-zero via its "two tasks
minimum" for `api`, so the Fargate half of the claim stands. The 7am-cold-start reasoning, which
is about the *database*, is what comes from the superseded ADR. Deciding where that rule now lives
— ADR-021, ADR-023, or a new ADR — is not mechanical.

**This matters:** Aurora Serverless v2 can scale to 0 ACU, and the only citable home for "do not
do that in production" is currently a withdrawn decision.

### F10. `Platform Choice.md` says it is undecided; everything else says it is decided
**Frontmatter line 5, lines 16–17, 170–185 · cat. 3 + 4**

Frontmatter read `status: proposal — awaiting Dave's decision`, and line 16 read *"Nothing is
written to those yet — this document is the analysis, not the decision."* All three target ADRs
were in fact amended or superseded, ADR-023 was written, and `Fleetco Overview.md:85` labels this

- Frontmatter status and the line-16 sentence: `APPLIED` — both now record ADR-023.
- The "What Would Have to Change" section (170–185), which is a to-do list of work already

### F12. All-in monthly cost: three live figures
**cat. 1**

Per Dave's instruction, `Stack Evaluation.md`'s cost model is the source of truth.

| Figure | Where | Resolution |
|---|---|---|
| **$200–385** | `Stack Evaluation.md:141`, `Fleetco Overview.md:48`, `Roadmap.md:156` | **Current.** Arithmetic verified; includes the non-production line. Unchanged |
| $175–330 | `Architecture Decisions.md:605` (ADR-023) | `APPLIED` → $200–385 |
| $175–330 | `Platform Choice.md:165` | `APPLIED` → $200–385, by adding the non-production row verbatim from Stack Evaluation |
| $200–360 | `Platform Choice.md:167` | `DEFERRED` — see below |

Both stale figures were correct when written; they predate ADR-024, which added non-production
environments to the model. The $109–174 AWS subtotal is identical in all three documents and
needed no change.

Downstream percentage: `Platform Choice.md:168` read "under 7% of FullBay's $5,000" — correct for
$330, wrong for $385. `APPLIED` → "under 8%", matching `Stack Evaluation.md:148`.

**Two things deliberately left:**

- ADR-023's wording was "Cost **drops slightly**, to $175–330." Correcting the figure alone would
  have left a false direction claim, so the verb was changed to "settles at" and a pointer to
  `Stack Evaluation` added. This is the one place the fix pass touched wording rather than a
  number, and it was unavoidable once the figure moved.
- `Platform Choice.md:167`'s comparison against "the current Neon-based plan at $200–360" is
  `DEFERRED`. That figure appears nowhere else in the knowledgebase and cannot be verified or
  reconstructed from the documents. **Known side effect: with the total now corrected to $200–385,
  this sentence reads inconsistently — it claims the AWS plan is "slightly cheaper" than a
  $200–360 alternative.** Rewriting the comparison would mean inventing a number or authoring new
  prose, so it is flagged here instead.

One correction to the brief's calibration: the other two figures named there are not all-in
monthly costs. **$188–258** is FullBay's published per-shop list price
(`FullBay Analysis.md:63–68`, `Competitive Landscape.md:60`), and **$150–200** is the EKS
comparison (`Architecture Decisions.md:500`, `Hosting and Deployment.md:169`). Both are correct
where they sit and were left alone.

### F13. FullBay's $5,000/month is never reconciled with FullBay's own $188–258 list price
**`Fleetco Overview.md:49`, `Project Brief.md:78`, `FullBay Analysis.md:63–73` · cat. 6 ·
`DEFERRED`**

`$5,000/month` is marked `Confirmed`, described as "the real market signal" and "a real forcing
function," and used as the denominator in every cost comparison. The same knowledgebase records
FullBay's public pricing at $188/mo Basic and $258/mo Pro, and uses that range to set the resale
revenue ceiling — a calculation that directly undercuts the $5,000 figure.

A 20–26x gap with no explanation offered. Plausibly per-user scaling, Elite/Enterprise quoting, or
multiple shops, but nothing says so, and `FullBay Analysis.md:141` has an unlinked open item
("confirm per-user vs flat pricing"). Either the $5,000 needs its composition recorded or it
should lose `Confirmed` status. Not mechanical: no document contains the answer.

### F16. `Domain Model.md:39–45` omits the day-one identity schema
**cat. 3 · `DEFERRED`**

The Tenancy & Identity block is `Tenant / User / Membership / Role`. Missing: `Identity` and
`SsoConnection`, both P0 non-negotiables per ADR-016 and `Tenancy Model.md:174–175`. Its
`Membership` also lacks `plane` and `customer_id`, which `Auth and Identity.md:173` specifies —
and `customer_id` on membership is the mechanism that scopes portal users, the highest-risk field
in the system. It is also the only block with no schema prefix while every other block has one.

An agent generating schema from this document would produce a model that cannot express portal
scoping. Deferred: adding entities is design work, not a mechanical correction.

### F17. `Environments.md` contradicts itself on non-production cost
**Line 95 vs line 114 · cat. 1 · `APPLIED`**

Line 95 claimed "~$20–50 total"; the table at 114 says "$60–65, or ~$20–30 with only `staging`."
The table's arithmetic ($20 + $30 + $10–15) is self-consistent, so line 95 was the error. Changed
to "~$20–65", which also matches ADR-024:642's "roughly $20–65".

**Residual discrepancy, deliberately left:** `Stack Evaluation.md:135` carries non-production as
$20–50. Correcting that row would change the $200–385 total, which Dave designated as the current
and correct figure, so it was left alone. Reconciling the two needs a decision about whether the
model assumes one non-production environment or two.

### F18. Impersonation still placed in the deferred vendor plane
**`Operations.md:140`, `Auth and Identity.md:70` · cat. 4 · `APPLIED`**

ADR-005's 2026-10-09 revision deferred the separate vendor plane entirely; phase one is "an admin
role inside the single application." Both documents still located impersonation there, so a reader
following them would build the deferred application. Stale location clauses struck in both — the
capability itself is unchanged and still required.

### F19. ADR-005's decision statement contradicts its own revision
**`Architecture Decisions.md:101–103` vs 110–115 · cat. 3 · `DEFERRED`**

The decision reads *"A separate vendor/operator plane with its own auth."* The revision below says
that consequence is "deferred." Unlike F8, the revision does not specify a replacement phrasing
for the decision line, so amending it is a judgment call.

### F20. Q17 is both "settled on the merits" and "would flip to GCP"
**`Open Questions.md:118–120` vs `Hosting and Deployment.md:19–21` · cat. 3 · `DEFERRED`**

Open Questions: *"ADR-021 and ADR-023 settled on AWS on the merits… The remaining question is only
administrative."* Hosting: *"a GCP one would make Cloud Run the better pick."* ADR-021:455 splits
the difference. `Platform Choice.md:145` sides with Open Questions, and ADR-023's case (S3 Object
Lock, Aurora fast clone) has no GCP equivalent — so a GCP pivot would reopen far more than
hosting. Needs a decision about how open Q17 actually is.

### F21. `Roadmap.md:20` claim is false by its own table
**cat. 6 · `DEFERRED`**

*"Every open question maps to exactly one milestone below. Nothing is orphaned."* The map at
125–133 maps Q1→M1+M5, Q4→M1+M3, Q5→M3+M6, Q13→M2+M8, Q15→M2+M8, and M7 has no row at all. The
fix ("at least one") is small but this is a claim wrong on its merits rather than one of the four
approved buckets.

### F22. `Infrastructure Checklist.md:155` implies a double-count
**cat. 1 + 5 · `APPLIED`**

The table labelled Sentry / PostHog / uptime as *"Added to the [[Stack Evaluation]] model."* They
are already inside the Stack Evaluation total at lines 137–140; adding them again puts the all-in
figure at $230–470. The label was a wrong cross-reference — it misstates the relationship between
the two documents — and now reads "Already included in."

The `~$30–85` subtotal was left as written; the components sum to $26–86, which is rounding rather
than a conflict with another document.
